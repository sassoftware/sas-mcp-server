# Scaling the MCP server with user count — investigation

**Date:** 2026-08-10 · **Measured against:** a live cluster
(`helm release sas-mcp`, ns `sas-mcp`, v1.8.0, 1 replica)

---

## Verdict

**The MCP pod is not what you scale.** It is a thin async proxy: 40 concurrent
clients hammering it continuously cost **113m CPU and 23Mi of memory above
idle**. The pod could serve an entire department on a fraction of a core.

What scales with users is **SAS Viya**. Every distinct user gets a warm compute
session, and on this cluster each one is a pod requesting **150m CPU and ~550Mi
memory** (limits 4 CPU / 6Gi). Ten users cost ~1.5 CPU and ~5.5Gi on the Viya
side — roughly **36× the MCP pod's entire footprint**.

So the sizing question "how much do I give the MCP server per user" has a
slightly deflating answer: *almost nothing, and mostly memory not CPU*. The
question that matters is **how much Viya compute capacity the user population
needs**, and that is set by a formula in [Sizing](#sizing) below.

One thing did need changing on the MCP pod, and it was not driven by user count:
the original **512Mi memory limit was too tight for a single large report
export**. That is now raised to 1Gi and applied.

---

## Method

All numbers are from the live deployment. Pod metrics via `kubectl top`
(metrics-server); latency from the **nginx ingress access log**'s
`upstream_response_time`, which measures the server rather than my
laptop-to-cluster link. Load was generated by concurrent MCP clients driving
`tools/list` in a loop — deliberately, because `tools/list` never touches Viya,
so it isolates the pod's own cost from the Viya-side cost.

> **A correction worth recording.** My load client reported a 27% error rate and
> a 2.4 s median at concurrency 40, and my first instinct was that the server was
> choking. It was not. nginx logged **2,359 × 200 and exactly one 502** for the
> same window, with a 27 ms median. The errors and the latency were my own test
> client saturating over the WAN link. The server-side numbers below are the
> nginx ones; the client-side ones were measurement error.

## Measured: the MCP pod

| Load | CPU | Memory | Δ memory vs idle |
|---|---|---|---|
| Idle | 3–4m | 152Mi | — |
| 10 concurrent clients, continuous | 58–64m | 157Mi | +5Mi |
| 40 concurrent clients, continuous | 85–113m | 175Mi | +23Mi |

Server-side latency at 40 concurrent (n=2,411 requests):

| | |
|---|---|
| p50 | **27 ms** |
| p90 | **138 ms** |
| p99 | **5,265 ms** |
| Success | 2,359 / 2,411 (**99.96%**, one 502) |

Two things to read from this:

- **Memory per connection is ~0.5Mi.** Even 200 simultaneous clients would add
  only ~100Mi. Connection count is not a memory problem.
- **The p99 is 200× the p50.** Average CPU was only ~11% of a core, so this is
  not CPU exhaustion — it is head-of-line blocking on a single event loop when
  40 clients connect and serialize 75 tool schemas at once. It matters for
  *burst* behaviour (everyone opening their editor at 09:00), not throughput.

The continuous-loop workload is far harsher than reality: a real MCP client
calls `tools/list` once per session and is then idle between human turns.

## The real cost: one Viya compute session per user

`viya_utils._ComputeSessionCache` keys sessions on the JWT `sub` claim, so the
mapping is one warm compute session **per distinct user**, per compute context.
On this cluster each session is a `sas-compute-server-*` pod:

```
requests:  cpu 50m   + 100m    = 150m
           memory 300M + 250Mi ≈ 550Mi
limits:    cpu 2 + 2           = 4 CPU
           memory 2Gi + 4Gi    = 6Gi
```

**There is no TTL or eviction in the MCP cache.** It holds a session per user
until Viya's own inactivity timeout reaps it, at which point the next call finds
the session dead (`_session_is_alive`) and transparently creates a new one. That
is self-healing, and it means the sizing input is not "concurrent users" but:

> **Peak sessions ≈ distinct users active within the Viya compute-session idle
> timeout window.**

That timeout is the single most powerful sizing lever you have, and it is set on
the compute context, not in this repo. On a shared server a shorter idle timeout
directly reduces peak concurrent sessions — at the cost of more cold starts
(session spin-up took ~8 s in the smoke test).

## Sizing

### SAS Viya (the binding constraint)

Multiply peak concurrent sessions by the per-session request:

| Peak active users | Viya CPU (requests) | Viya memory (requests) |
|---|---|---|
| 5 | 0.75 | ~2.7Gi |
| 10 | 1.5 | ~5.4Gi |
| 25 | 3.75 | ~13.4Gi |
| 50 | 7.5 | ~26.9Gi |
| 100 | 15 | ~53.7Gi |

Requests are what the scheduler reserves; *limits* are 4 CPU / 6Gi per session,
so a few users running heavy SAS simultaneously can burst far above the request
line. Size the compute node pool on requests, but keep headroom for bursts.

### The MCP pod

Barely moves with user count. The binding term is **transient result buffers**,
not connections:

| Peak active users | CPU requests | CPU limit | Memory requests | Memory limit |
|---|---|---|---|---|
| ≤ 10 | 100m | **1** | 256Mi | **1Gi** |
| 10–50 | 250m | **1** | 384Mi | **1Gi** |
| 50–200 | 500m | **1** | 512Mi | **2Gi** |

**Limit CPU to one core, not less.** The chart and the manifests do so since
1.19.2; earlier versions set no CPU limit. The server is one Python process with
one event loop, so it cannot use much more than a core: a one-core limit caps the
pod if something goes wrong and never slows a request down. A live deployment
averaged 13m of CPU over 58 days, but its work comes in single-threaded bursts,
measured on 1.19.1 (2026-11-12):

| Burst | CPU time | Wall time under a 500m limit |
|---|---|---|
| Startup: imports, 115 tools and the views registered | 4.7 s | ~9.5 s |
| 40 clients listing tools at once | 1.6 s | ~3.2 s |
| A 25 MiB inline export, base64 and JSON only | 0.2 s | ~0.45 s |

Under a limit below one core, the kernel stops the process for the rest of each
100 ms period once its share is used up, so each burst takes proportionally
longer and every other request waits behind it — the p99 shown above, made
worse. For a busier pod raise the CPU request, as in the table; the limit stays
at one core. The bursts were measured on a workstation; a cluster vCPU is usually
slower, which makes them longer, not shorter.

## The one change that was actually urgent (now applied)

**The memory limit was raised from 512Mi to 1Gi.** This is not about user count.

`MAX_EXPORT_INLINE_BYTES` defaults to **25 MiB**: `export_report` returns a
binary export inline as an embedded resource. That payload gets base64-encoded
(×1.33) and JSON-serialized, so a single 25 MiB export can transiently need
several hundred MiB — against a 512Mi limit with 152Mi already resident at idle,
leaving ~360Mi of headroom. One large export could OOM-kill the pod; two
concurrent almost certainly would.

An OOM kill is not graceful: it is SIGKILL, so the lifespan never runs and every
warm compute session leaks until Viya reaps it.

```sh
helm upgrade sas-mcp deploy/helm/sas-mcp-server -n sas-mcp --reuse-values \
  --set resources.limits.memory=1Gi
```

Lower `MAX_EXPORT_INLINE_BYTES` instead (or as well) if inline exports are not
needed.

## The three tools that buffer big payloads

The "transient result buffers" term above is not abstract — it is three
specific tools, and they are the only ones worth briefing users on. Everything
else is bounded small: `query_data` caps at 10,000 rows, `get_castable_data`
defaults to 100, and `execute_sas_code` logs are paged.

| Tool | What is buffered in the pod | Bound |
|---|---|---|
| `export_report` | the whole binary export, then base64 (×1.33) plus JSON framing on top | `MAX_EXPORT_INLINE_BYTES`, default 25 MiB — the worst amplifier |
| `upload_data` / `upload_file` (`file_path`/`url` sources) | the whole source file, held while it is re-posted to Viya | `MAX_UPLOAD_BYTES`, default 100 MiB |
| `download_file` | the whole Files-service file | no code-side cap, but bounded in practice by Viya's own file-upload limit — everything in the Files service arrived under it |

**`MAX_UPLOAD_BYTES` defaults to 100 MiB to match SAS Viya's default 100 MB
file-upload limit**: a payload over the Viya cap would be refused upstream
anyway, so buffering it in the pod would spend memory on a guaranteed failure.
(Before this cap the `url` source was unbounded — one multi-GB fetch was an
OOM kill in a single call.) The `url` source is refused up front on a declared
`Content-Length`, and the cap is enforced again while the body streams in, so
an absent or lying header cannot blow past it. **If your Viya administrator
raises the Viya-side limit, raise `MAX_UPLOAD_BYTES` with it — and revisit the
pod memory limit at the same time**, since a single upload can transiently
hold roughly twice the payload size (the buffer plus the multipart body being
posted).

Practical guidance for teams sharing a deployment: route bulk data movement
through SAS itself (`execute_sas_code`, path-based caslibs +
`promote_table_to_memory`) rather than through the MCP response path, and keep
inline report exports small or disabled. A deployment that does not need the
file tools at all can drop them wholesale with `MCP_TIERS` (tier 2) — tools
that are not registered cannot OOM anything.

## When one replica stops being enough

On these numbers, not for a long time — the pod would serve hundreds of users
before CPU or memory bound. You would hit it sooner for **availability** reasons
(a single pod is a single point of failure, and any restart drops every warm
session) than for capacity.

Scaling out is still blocked by the two issues in `K8S-DEPLOYMENT.md`, and both
are code changes rather than configuration:

1. **OAuth client registrations** are a per-pod file-tree store. `OAuthProxy` takes
   a `client_storage=` argument; wiring it to Redis would fix this.
2. **The compute-session cache** is in-process, so the same user landing on a
   different pod creates a second Viya session — which is the expensive resource,
   so replicas multiply the dominant cost. Session affinity at the ingress
   (`nginx.ingress.kubernetes.io/affinity: cookie`) would mitigate both, and is
   the cheapest first step if you ever go to 2+ replicas.

Note the perverse incentive: because each replica keeps its own warm sessions,
**scaling the MCP server out increases Viya load** rather than spreading it.
Fix the shared-state issues first, or use affinity.

## Caveats

- **Single identity.** All load came from one Viya user, so all simulated clients
  shared one compute session. That isolates the pod-side measurement cleanly, but
  it means the per-user Viya cost is derived from the *observed pod specs* of real
  compute sessions rather than measured under a multi-user load.
- **`tools/list` as the load shape** is CPU-heavy (75 schemas) but touches no
  Viya API, so it over-states pod CPU per call and under-states end-to-end
  latency for real tool calls, which are dominated by Viya round-trips
  (~1.2 s median in earlier benchmarking).
- **p99 is one burst.** 5.3 s reflects 40 clients connecting simultaneously, not
  steady state. It has not been characterised across repeated runs.
- **The Viya compute-session idle timeout was not read** from the context
  configuration — the context returned no explicit attributes, so the deployment
  default applies. Confirm it before using the sizing formula, since it sets
  peak session count directly.
- Telemetry is **off** in this deployment. Turning it on adds a JSONL append per
  tool call, offloaded to a worker thread; it was not measured here.
