## [Unreleased]

## [1.14.2] - 2026-09-11

### Fixed
- **`execute_sas_code` reported every failed job submission as the single word `'id'`.** (#59, #55) The submit was the one request in the compute path that never checked its HTTP status, so Viya's error body was parsed as though it were a job: `job["id"]` raised a `KeyError` whose entire message is `id`, and the caller got `Error calling tool 'execute_sas_code': 'id'` while the actual reason — "The session is not available.", an authorization message, whatever it was — was discarded. Reported from the field against GitHub Copilot, where the model then retried simpler and simpler SAS code against an error that had nothing to do with the code.
- **A failed log fetch was reported as a job that produced no output.** (#59, #55) The log and listing endpoints are paged, and the page reader took `items` off the response without checking it first — on an error body that yields `[]`, which the short-page test reads as "end of log". So a job whose log could not be read came back with a state and an empty log rather than an error, which for audit-style work silently loses the deliverable.
- **A compute session dying mid-job left `execute_sas_code` polling forever.** (#59, #55) The job state is read as plain text, so an unchecked error body became the "state" — never one of the terminal values, so the poll loop simply continued, every two seconds, for as long as the process lived. All three now check the response first; the poll deliberately has no wall-clock cap alongside that, since a legitimate SAS job can run for hours.
- **A 409 when listing a caslib's tables read as a permissions problem, and is not one.** (#59, #56) casManagement answers a caslib read with 409 when CAS cannot connect to the library's *underlying data source* — verified against two database caslibs on one deployment, postgres (`password authentication failed`) and Oracle (`ORA-00257: archiver error`), both arriving as the same 409 behind the same "connection to the data source driver failed" text. The status on its own points the reader at authorization, so the natural next step is to check caslib permissions, find them correct, and be stuck. `list_castables`, `list_source_tables`, `get_castable_info` and `get_castable_columns` now keep Viya's own reason and add what it means: this is the data source, not your access rights — confirm you can open the caslib directly in SAS Viya, and if it fails there too the connection or its stored credentials need an administrator. Reads only: a `POST` to the same collection answers 409 for "that table already exists", which is unchanged.
- **Signing in from GitHub Copilot CLI failed before Viya was ever contacted.** (#58) The callback was refused with `Redirect URI 'http://127.0.0.1:52505/' does not match CIMD redirect_uris`. An MCP client opens a fresh loopback port for every sign-in, and FastMCP 4.0 enables CIMD (Client ID Metadata Document) by default: a client whose `client_id` is an HTTPS URL has its callback checked against the redirect URIs in its own published document, with no exemption for varying loopback ports — so the check could never pass. It cannot be widened from this side either, since the document check runs first and `allowed_client_redirect_uris` only narrows what the document already permits. The proxy now sets `enable_cimd=False`, putting URL-shaped client IDs on the ordinary dynamic-registration path, which does allow loopback ports to vary (RFC 8252 §7.3) and is the path every other MCP client already uses. Verified against GitHub Copilot CLI 1.0.83. Note the trade: the server no longer advertises `client_id_metadata_document_supported`, and `private_key_jwt` drops out of the advertised token-endpoint auth methods — both accurate, since neither is supported with CIMD off. Reported and fixed by @bteleuca.

## [1.14.1] - 2026-09-09

### Fixed
- **Browser sign-in failed at the last step on every HTTP deployment since v1.12.0.** (#54) The login completed, the callback ran, and the token exchange was then rejected by SAS Logon with `invalid_client: Missing credentials`. The FastMCP 4.0 upgrade replaced authlib's OAuth2 client with FastMCP's own, and the replacement defaults to `client_secret_basic` whether or not a client secret exists — where authlib had chosen `none` when there was none. `sas-mcp` is registered as a public client with no secret, so `upstream_client_secret=None` was interpolated into the credential and sent as `Basic base64("sas-mcp:None")`, offering the literal word "None" as the password. The proxy now declares `token_endpoint_auth_method="none"`, which is the RFC 6749 method for a public client and what authlib inferred on its own before the upgrade. Token *refresh* failed the same way and is fixed with it. stdio mode was never affected (it signs in through `auth_login.py`, which has its own token request), nor were clients presenting a raw Viya JWT with `ALLOW_RAW_BEARER`. Reported and fixed by @bteleuca.

## [1.14.0] - 2026-09-07

### Fixed
- **A term left unpublished by `create_glossary_term(publish=false)` could not be edited, and could never be published.** (#52) A draft is a *separate resource*: the ordinary `/glossary/terms/{id}` answers `GET` and `DELETE` for one, so it looked reachable, but a `PUT` there is a flat 404 — `update_glossary_term` could not change a draft at all, and nothing could promote one. The draft's own `links` say where it lives: `PUT /glossary/terms/{id}/draft` to edit and `PUT /glossary/terms/{id}/draft/state?action=publish` to publish, neither of them documented anywhere. Updates now route to the draft when the term is one, and `update_glossary_term(publish=true)` promotes it — on its own, or alongside a final edit. Publishing a term that is already published is reported rather than attempted, since the service answers that with a 404 (errorCode 76900) that reads as "the term is gone". Verified live through the whole cycle: create unpublished, confirm it is hidden from the listing without `include_drafts`, edit, publish, read the edit back.
- **The bulk import put the term's definition into its description, and left the definition holding the term's own name.** (#52) Found by a second pass over the same deployment that reported everything above. The importer's `Description` column is the *description*; `Definition` is a separate system column, and with no `Definition` column at all the service fills the field in with the term's name. So an imported 122-term hierarchy came back with every definition reading like a label and every description holding the text meant for the definition — the field a reader actually sees, wrong on every row. Both columns are now written from the row's own `definition` and `description`. Verified live against a term type carrying an attribute labelled `Definition`: the column set the term's definition and left the attribute empty, which is also why `Definition` joins the system-column list a custom attribute may not collide with.
- **A numeric offset on a `time` attribute was dropped rather than converted, storing a value that was silently wrong.** (#52) `09:15:00+02:00` was stored as `09:15:00Z` — two hours out, with nothing to say so — while the same offset on a `date-time` converted correctly. The offset is now applied, as it always was for a date-time, wrapping within the day since a time attribute carries no date; an impossible time (`25:00:00`) is rejected by name rather than wrapped into a plausible-looking one.
- **`""` did not clear a boolean attribute; it produced a Viya rejection instead.** (#52) `update_glossary_term` documents `""` as "clear this attribute", but the glossary has no empty boolean and answers `The value "" for the field "<label>" is invalid`. That is now said here, before the call, naming the attribute and what to pass instead.
- **A required boolean set to `False` was reported as a missing required attribute**, refusing an edit over a value that was there all along. (#52) The emptiness test read `value or ""`, under which `False` is indistinguishable from unset. Found while re-checking the required-attribute handling above rather than in the field; a term type with a mandatory boolean would have hit it on every update.
- **The bulk import did not check required attributes, so a row missing one failed inside the job** with Viya's `The value "Owner" for the field "attributes" is invalid` — after the rest of the batch had already been committed. (#52) `create_glossary_term` has always made this check; the import now makes the same one per row, before anything is sent, keeping the batch all-or-nothing as it already was for value formats. A required attribute that declares a **default** is not treated as missing on create or import, because the service fills it in — verified live: a row omitting one came back holding the default.
- **Renaming a term type's attribute silently orphaned every stored value.** (#52) Attributes were matched to the existing ones by label only, so a new label matched nothing, was added under a fresh identifier, and left each term's value behind under the old one — readable as nothing. A spec may now carry `attribute_id` (as `get_glossary_term_type` returns it) to say which attribute it is, leaving `label` free to be the new name; an unknown id is refused rather than quietly minting a new attribute, and a rename onto a label another attribute already holds is refused rather than producing two of the same name.
- **Boolean attributes could never be set on a glossary term.** (#52) Every attribute value was coerced to a string, so a boolean travelled as `"true"` and Viya rejected it — `The value "true" for the field "<label>" is invalid` — on both create and update. Only the term type's own default was ever stored, which made any term type carrying a boolean unusable through MCP. Booleans now travel as JSON booleans, verified end to end against a live glossary. Reported from a session that built out a real glossary; the same report is the source of everything below.
- **Multi-select attributes could not take a list.** (#52) A Python list was sent as its `str()` (`"['1', 'test']"`) and rejected. Viya stores a multi-select as its selected items joined with `,` and no spaces — it rejects a JSON array, `"a, b"` and `"a;b"` alike — so the join now happens in the tool: pass `["EMEA", "APAC"]`, get `EMEA,APAC` on the wire, and a list back from `get_glossary_term`. Each item is checked against the type's allowed values first, because Viya's own rejection names the attribute but never which item was wrong.
- **Date, date-time and time values were forwarded unchecked** and came back as bare HTTP 400s. (#52) Viya accepts exactly one spelling of each — `yyyy-mm-dd`, `yyyy-mm-ddThh:mm:ssZ`, `hh:mm:ssZ` — with the `Z` and the seconds mandatory and numeric offsets rejected outright. The recoverable cases are now normalised rather than forwarded (a bare date becomes midnight UTC, a missing `Z` or missing seconds are supplied, and a `+02:00` offset is converted to the same instant in UTC); the rest are rejected by name, with the expected format quoted.
- **An attribute made required after a term existed broke every later update of that term.** (#52) An update is a whole-resource PUT, so it replays attributes the caller never mentioned; if one of those had since become required and was empty, Viya rejected the write naming *that* attribute — while the caller was editing something else. The merged term is now checked first and the failure explains which attribute and why. Relatedly, a required attribute supplied as `""` is treated as missing on create, since that is exactly what the glossary stores for an unset one.
- **Viya errors arrived behind two lines of HTTP boilerplate.** (#52) Every failure led with httpx's status phrase, the full URL and a link to the MDN page for the status code, ahead of the one line that says what was actually wrong. Errors now read `HTTP 400 from POST /glossary/terms — Viya reported: ...`. Affects every tier, not just the glossary.
- **Assigning a term to a table the catalog indexed *without* its columns reported a wrong column name.** (#52) With no columns indexed, every name looks wrong and the error listed an empty set of alternatives. It now names the indexing gap and points at `catalog_run_agent`.

### Added
- **`import_glossary_terms` names the term each row became, and says which rows were actually new.** (#52) The result carried `order` and tallies but no ids, so anything a caller wanted to do next — assign an asset, re-parent, read a term back — meant a search per term, which gives back most of the round trips the bulk import exists to remove. `terms` now carries `{name, path, term_id, existed}` per row, resolved in one filtered request per 40 distinct names: sibling names are unique, so a `(parentId, name)` index over the candidates rebuilds the hierarchy and every row's path walks down it. On a 122-term import that is about four requests rather than 122.
  - **The same pass fixes what `created` was hiding.** A row naming a term that already exists at that path is not created — with `update_existing` false the existing term is left untouched, with it true the term is replaced — but the job counts it as `successful` either way, so a re-import of a 122-term hierarchy reported 122 created and changed nothing. The job's own `creationTimeStamp` separates the two: a term older than the job was already there. `new` and `already_existed` report the split, `existed` says which is which per row, and a note spells out what happened to the rest. `created` keeps its old meaning — rows the job accepted — and the raw `counts` map is returned verbatim beside it.
  - Resolution never costs the import: a row whose id cannot be found keeps its place with `term_id: null` and the note names it, rather than the whole call failing after the terms are already committed.
- **`update_glossary_term` returns `parent_id`.** (#52) A re-parent was otherwise unconfirmable without a second `get_glossary_term`.
- **`delete_glossary_term` says there is no cascade.** (#52) Its description implied deleting a parent took its children with it; the glossary refuses the call outright with `Cannot delete a term/draft with existing children`. It now says so and points at `list_glossary_terms(parent_id=...)` for deleting a subtree leaf-first.
- **`import_glossary_terms` builds a whole hierarchy in one call.** (#52) Creating terms one at a time means a call per term *and* a wait between levels, because a child needs its parent's id from the previous response — a reported 122-term hierarchy took 122 sequential calls. This wraps the glossary's own bulk import (`POST /glossary/importTerms`), so parents are named rather than threaded by id: give each row a `name` and, for a child, a `parent` naming another row in the batch or the path of an existing term. Rows may be given in any order and are sorted so every parent precedes its children. A live three-level import with custom attributes, given leaf-first, came back correctly parented; 60 terms took one call.
  - **Attribute values keep the same forms as `create_glossary_term`** — `True`/`False`, a list for a multi-select — and are validated per term type *before* the CSV is built, so a bad value fails locally rather than as one row of a job log.
  - **A row can fail while the rest succeed, and the job still reports `completed`.** The result carries `created`, `failed` and a `failures` list naming each bad row, its row number and the reason, read from the job log — the only place the service records them. A non-empty `failures` is a partial import: the successful rows are already committed.
  - **An attribute whose label collides with a CSV system column** (`Name`, `Type`, `Path`, `Definition`, `Description`, `Requirements`, `Status`) is refused up front, because the importer would read that column as the term's own field and silently skip the attribute — then reject the term for missing it, which is what the first probe of this endpoint did.
- **`update_glossary_term` can move a term to a different parent.** (#52) `parent_id` re-parents it, `""` promotes it to a root. **A published term's parent *can* be changed** — this was previously documented here as an API limitation, and that was wrong: a `PUT` with a changed `parentId` is accepted, verified live on a published term.
- **Term types can now be designed through MCP, not only read.** (#52) `create_glossary_term_type`, `update_glossary_term_type` and `delete_glossary_term_type` complete the tier: a glossary could previously be read and populated through these tools but never *designed* through them, so any deployment wanting a custom type needed a SAS UI step first. Attributes are declared as `{"label": ..., "type": ...}` plus optional `required`, `allowed_values`, `default` and `description`.
  - **An edit keeps each attribute's identifier.** Attributes are matched to the existing ones by label, and the identifier is carried over — which matters more than it looks, because every term's stored values are filed under it. Re-minting one leaves each existing term's value orphaned under a key nothing names any more. Verified live: widening a single-select's options and adding a new attribute left an existing term reading all of its values.
  - **The identifiers are generated here because the API will not.** Omitting them fails with `The value for field "name" must be unique`, which names neither the attribute nor the real problem.
  - Attributes the caller does not mention survive an update; `remove_attributes` drops one by label. A `single-select` or `multi-select` declared with no `allowed_values` is refused, since nothing could ever be stored in it — the service accepts that definition happily. `label` defaults from `name`, which the API leaves empty rather than defaulting, showing as a blank in the UI.
  - `delete_glossary_term_type` refuses while terms still use the type, naming how many and how to list them; `force` overrides.
- **`list_glossary_terms` and `search_glossary_terms` can return attribute values, and `list_glossary_terms` can filter on them.** (#52) Neither previously returned attributes or could filter on one, so *"which terms need masking"* or *"which terms are used in Risk"* meant fetching every term one at a time. `include_attributes` now returns them named, and `attribute_filter` keeps only the terms that match — `{"Used in Risk": true}`, `{"Regions": "EMEA"}` — with clauses ANDed and a multi-select matching when it *contains* the value.
  - **On the listing, attributes are free.** The list representation already carries the raw UUID-keyed map, so decoding costs one call per *distinct term type* on the page — normally one — and none per term. On `search_glossary_terms` the catalog index does not carry them, so they are read from the glossary in one batched call per 40 hits rather than one per hit; it stays off by default for that reason.
  - **The glossary cannot filter on attribute values, so this filters here.** Every spelling of `eq(attributes.<uuid>,…)` is rejected as an invalid filter, so `attribute_filter` scans pages the server *can* return and the result says how far it got: `scanned`, `scan_complete`, and a `next_start` when the scan was capped. A short list is otherwise indistinguishable from a complete answer. Narrowing with `term_type` narrows the scan too — on a live 1,720-term glossary, filtering one term type answered in 1.3s against 8.3s unscoped.
  - **A mistyped filter label is refused rather than matching nothing**, listing the labels that do exist — the failure mode worth preventing, since an empty result reads as a real answer.
- **`get_glossary_term_type` now reports a `value_format` per attribute.** (#52) The glossary service publishes no OpenAPI document and several attribute types accept exactly one spelling, so the contract a caller needs was previously discoverable only by provoking a 400. Each attribute now states its accepted form alongside its type, required flag and allowed values.


## [1.13.0] - 2026-09-04

### Added
- **Tier 9 — Business Glossary: twelve tools for reading and authoring the SAS Business Glossary, and for linking its terms to the columns they describe.** (#51) Tier 1 tells you a column is called `CD_NAC_RSK`; this tells you what that means and who says so. `search_glossary_terms` (ranked free text over names *and* definitions), `list_glossary_terms` (structural — by type, by parent, by name fragment), `get_glossary_term`, `list_glossary_term_types` / `get_glossary_term_type`, `list_term_assets` and `list_table_terms` for the two directions of term↔column linkage, and `create_glossary_term`, `update_glossary_term`, `delete_glossary_term`, `assign_glossary_term`, `unassign_glossary_term` for authoring. Enable it alone with `MCP_TIERS=9`; seven of the twelve survive `MCP_READ_ONLY`.
  - **A term has two ids, and the tools hide it.** A term exists as a Glossary object *and* as an Information Catalog entity, with **different** identifiers — the glossary id is what you read and write, the catalog id is what asset relationships point at and what catalog search returns. Every tool returns both, under `term_id` and `catalog_entity_id`. The bridge is the catalog entity's `resourceId`, which is **absent from the default representation**: read the entity as anything but `application/vnd.sas.metadata.instance.entity+json` and the field simply is not there, so a bridge built on the default reads as "this term is not mirrored" instead of failing.
  - **Custom attributes are read and written by name.** The API stores a term's attributes as `{attribute-definition-uuid: value}`, with the human label held on the *term type* — unreadable as returned, and unwriteable without a second lookup. These tools resolve UUID→label on read and label→UUID on write, drop the empty values the glossary stores for every declared attribute, validate single-select values and required attributes *before* calling Viya, and coerce booleans to the `"true"`/`"false"` strings the glossary stores (passing a real `bool` is accepted but displays as `True`). An unknown attribute is rejected with the valid labels listed, which is a mistake a model can correct; an HTTP 400 is not.
  - **`create_glossary_term` publishes by default.** The underlying API defaults to creating a *draft*, visible to nobody but its author — almost never what "create a term" means. `publish=false` still gets the draft.
  - **`update_glossary_term` merges instead of replacing.** The API's update is a whole-resource PUT, so it reads the current term first and merges: an omitted argument leaves that field alone rather than blanking it, and attributes merge one at a time.
  - **Term↔asset traversal is one request per batch, not one per link.** The link is a catalog `glossaryTermAsset` relationship whose endpoints are only present under `application/vnd.sas.metadata.instance.relationship+json` — supplied here as the collection's `Accept-Item`, so a filtered query returns the endpoints directly. Reading them from individual instances instead costs a round trip per link: on a live 13-column table the batched form answers in one call where the per-link form needs about twenty-five. Lookups are chunked so a wide table cannot build a filter the gateway rejects — a transport detail, invisible in the results. What a caller *can* control is `list_term_assets`' `limit`/`start`: it reports the term's **total** asset count alongside the page, plus `truncated` and the exact `next_start` to pass, so a term governing thousands of columns can be read in full by paging rather than being silently cut off at a fixed ceiling.
  - **Shared rather than re-implemented.** The pure transforms — the id bridge, the attribute encode/decode and its validation, the id chunking — live in `helpers/glossary_helpers.py` alongside the other tiers' helper modules, so the rules can be read and tested without the request plumbing around them. Filter-literal escaping moved to a new `viya_client.filter_literal`, which `contains_filter` now uses too, so the Viya quoting rule is stated once instead of per call site; a batched `viya_client.in_filter` joins it.
  - Terms assigned this way are also reachable from Tier 1's `catalog_search` via the `Column.term:"<term name>"` facet on the `datasets` index (matching is case-insensitive), which returns the tables carrying a term without resolving individual columns.

## [1.12.0] - 2026-09-01

### Changed
- **Upgraded to FastMCP 4.0, which is now the minimum.** (#50) The pin moves from `fastmcp>=3.0.0,<4.0.0` to `fastmcp>=4.0.0,<5.0.0`, bringing `mcp` 2.x and FastMCP 4's HTTP client, `httpx2`, alongside the `httpx` this project uses directly. FastMCP 4.0 needs no changes to how tools, prompts, middleware, tiers, read-only mode or the OAuth proxy are written — the whole test suite passes on it unaltered. **This is not a drop-in for an existing checkout: `uv sync` (or a container rebuild) is required, and running this code against FastMCP 3.x is no longer supported** — see the annotation rename below for why that combination fails quietly rather than loudly.
- **Tool annotations now use the MCP SDK v2 snake_case field names** (`read_only_hint`, `destructive_hint`, `idempotent_hint`, `open_world_hint`, and `input_schema` in the tests) (#50), matching the rename in the SDK that ships with FastMCP 4. **Clients are unaffected:** the wire format is still the spec's camelCase (`readOnlyHint` and friends), because SDK v2 keeps those as serialization aliases — verified against a real `tools/list` response, where all 75 tools carry the camelCase keys and 43 report `readOnlyHint: true` exactly as before.
- **`SSL_VERIFY=false` continues to cover FastMCP's own HTTPS calls.** (#50) FastMCP 4 dropped `httpx` for `httpx2`, so a patch that reached only `httpx` would have stopped covering the JWKS fetch and the OAuth token exchange — failing inside the auth layer as a 401 or a connect error. `ssl_patch` already patched both, so no change was needed here; this release confirms it against 4.0 rather than a pre-release.

### Added
- **Guards against a tool-annotation rename silently blanking what clients are told.** (#50) The landing page reads its read-only and destructive badges with `getattr(..., None)`, which cannot tell "this tool declares nothing" from "this field was renamed", so a future rename would have blanked every badge with nothing failing. Two tests now assert the field names exist on `ToolAnnotations`, and two more assert the *serialized* payload uses the spec's camelCase keys and that every read-only and destructive tool still advertises itself as such. This is the shape of failure the rename would otherwise have caused on FastMCP 3.x: the annotations are accepted, read back correctly by the model, and reach clients under non-spec names, so all 43 read-only tools quietly look writable.

## [1.11.2] - 2026-08-31

### Added
- **`examples/register_mcp_client.py` gained `--dry-run`, extra redirect URIs, and an unattended mode.** (#49) `--dry-run` prints the redirect URIs and the exact request body that would be POSTed and exits without contacting Viya or needing credentials, so the destructive step can be checked before it runs against a shared client; the preview shares one `client_payload()` with the real call, so what it shows is what would be sent. `--redirect-uri` (repeatable) and `MCP_EXTRA_REDIRECT_URIS` (comma separated) register additional callbacks for a deployment answering on more than one URL, de-duplicated and order-preserving, with a warning for any URI that does not end in `/auth/callback`. `VIYA_USERNAME` / `VIYA_PASSWORD` skip the prompts — the same names the integration tests already use — and the script prints which user it is acting as, since that user needs admin rights.

### Changed
- **`examples/register_mcp_client.py` no longer risks leaving a deployment with no OAuth client at all.** (#49) Registering means deleting the client and re-creating it, so any failure in between — insufficient admin scope, a tenant policy rejecting `allowpublic`, a dropped connection — used to leave nothing behind, locking every user out of a shared deployment with no record of what had been there. It now reads the current definition first, prints it, saves a timestamped copy to the temp directory, and on failure tells you the client is gone and prints the exact `curl` that puts the previous definition back (filtered to the fields SASLogon accepts on create; note that `client_secret` is never returned by a read, so only a public client — which is what this registers — can be restored this way). A failure *before* anything is destroyed now says so explicitly.
- **"Verifying registration" actually verifies.** (#49) It used to print six fields and exit `0` no matter what they said, which is why a mismatched redirect URI could look like a clean run — the report that prompted this fix noted the registration only "appeared" correct. It now asserts every expected redirect URI is present in what Viya stored, prints `OK` or a `FAIL` naming the missing URIs and the sign-in error they will cause, and returns a non-zero exit code. Handles Viya returning `redirect_uri` as a bare string as well as a list.
- **The script now exits non-zero on every failure path** (missing `VIYA_ENDPOINT`, rejected credentials, unreadable client, failed delete, failed registration, failed verification) (#49), so runbooks, `&&` chains and CI can tell success from failure. Previously every one of these printed a message and exited `0`.
- **Failures now read as causes rather than tracebacks.** (#49) An `httpx` error is rendered with its status, what that status means for this endpoint (403 → the user may not manage OAuth clients and needs `clients.admin`; 401 → credentials rejected; 409 → the client already exists) and Viya's own response body, instead of an `HTTPStatusError` stack trace. A connection failure with no response says to check `VIYA_ENDPOINT`, network access and `SSL_VERIFY`.
- **Smaller sharp edges in the same script:** (#49) `SSL_VERIFY=false` now prints a warning that TLS verification is disabled rather than doing it silently; a non-numeric `HOST_PORT` reports which variable is wrong instead of raising `ValueError` during import; and the credential prompt no longer dies with `EOFError` where there is nothing to read — `stdin.isatty()` turned out to be an unreliable guard on its own (it can claim a terminal that has no input), so the prompts themselves fail into the same "set `VIYA_USERNAME` and `VIYA_PASSWORD`" message, and Ctrl-C exits cleanly.

### Fixed
- **`examples/register_mcp_client.py` ignored `MCP_BASE_URL`, so a server reachable at an external URL could never finish signing in.** (#49) The script hardcoded `http://localhost:{HOST_PORT}/auth/callback` as the only redirect URI it registered with SAS Logon, while `config.py` correctly derives what the *running* server presents from `MCP_BASE_URL`. Point `.env` at a shared host, reverse proxy, tunnel or Kubernetes deployment and the two disagree: the server sends the external callback, Viya only ever knew the localhost one, and **Viya** rejects the authorization request *after* the user has already signed in — `Invalid redirect ... did not match one of the registered values` — leaving no `/token` and no `/auth/callback` in the server's own log. Re-running the old script could not repair it either, because it re-registered the same wrong URI. It now derives the callback from `MCP_BASE_URL` using the same rule as `config.py` (empty, or a value left as a commented-out placeholder, falls back to localhost) and registers the external URL **alongside** `localhost`, so a single registration serves both a shared deployment and local development. Found on a shared deployment where teammates reached SAS Logon, authenticated, and were never redirected back.

Those clients cannot sign in without these routes. They claim paths on a shared host, so the knob exists to turn them off.

It is not: `MCP_BASE_URL` carrying a path is enough, because the server advertises every OAuth endpoint relative to it. The section now says so, and states the two root paths the RFCs pin in place regardless.

### Added

  - **Tool-declared failures are recorded as failures, in every mode.** This repo's tools return failures as *data* (`{"status": "apply_failed", ...}`), which the MCP layer sees as success — so every VA rejection in a v1 trace logged as a win and the measured failure rate was fiction. It is **re-emitted every 1000 records**, because a header written once per process is discarded outright when rotation drops that file, orphaning every later record. Every header field is a run constant — including `ts`, which is process start, not first use — so all emissions are byte-identical and a consumer may take any one.

### Changed
- **`COLLECTION_LOG_RESULTS` is tri-state — `never` | `failures` | `always` — and now defaults to `failures`** (#40). Full (capped + redacted) result contents are recorded only when the call errored at the MCP layer or the tool declared a failure; successes stay shape-only. Failure diagnostics are the highest-value trace data and are the least likely to carry table rows, so this keeps the privacy posture that matters while making the log readable — under the old `never` default a success and a failure were indistinguishable. `true`/`false` remain aliases for `always`/`never`, and an unrecognised value warns and falls back to `never`.

Under HTTP a run spans every client the process served, and `client_name`/`client_version` are the only discriminator — two users on the same client software share one `run_id` and one `seq` counter. ## [1.8.0] - 2026-08-07

### Added
- **`query_data` — one FedSQL surface over CAS and compute data** (#38). Run a `SELECT` against a caslib table or a SAS library table and get structured rows back: `{columns, rows, count, start, limit, truncated, column_types}`, matching the `get_castable_data` envelope. `target` picks the namespace (`cas` → `caslib.table`, `compute` → `libref.table`); joins (inner/left/right/full/cross), subqueries, derived tables, aggregation, and `UNION` all work. Brings the tool count to 75.
  - **The row cap is the tool's, not the query's.** `limit` (integer, default 100, max 10000) is injected as an outer `LIMIT` so it is enforced *server-side*; any `LIMIT` in the submitted SQL is ignored, because CAS silently *discards* a malformed one (`limit 'two'` returns the entire table) — verified live. `start` pages, and `truncated` reports whether more rows exist.
  - **`create_view_name` returns the query as `CREATE VIEW` text** for the caller to run themselves; it is never executed (CAS accepts only SELECT/CTAS/DROP TABLE).
  - **Reads only, and checked before anything is submitted:** the query must be a single `SELECT`; `INSERT`/`UPDATE`/`DELETE`/`CREATE`/`DROP`/`ALTER`/`MERGE`/… are refused anywhere in it; statement separators, unbalanced parentheses, unterminated block comments, and **unbalanced quotes** are rejected (an unterminated literal is the one input that would *hang* rather than fail — SAS keeps consuming while it looks for the closing quote, wedging the warm compute session for every later call, `execute_sas_code` included); and **SAS macro triggers (`%`, `&`) are rejected outside single-quoted strings** — the macro processor would expand them before FedSQL ever ran, which is the one channel that escapes SQL entirely. `LIKE '%pattern%'` in single quotes still works.
  - **Values keep their types.** Results are read from a format-stripped copy so numerics stay numeric and missing values are `null` rather than the padded `"        ."` string a formatted read returns, while column formats (taken from the unstripped table) restore dates as ISO text. Numerics carry ~10–11 significant digits.
  - **Errors are mapped, not dumped:** `table_not_found`, `column_not_found`, `schema_not_found`, `ambiguous_column`, `syntax_error`, `unsupported_statement`, `invalid_query`, `query_failed` — each with the next action, including FedSQL-specific rewrites (no `WITH`/CTE → derived table; no `MERGE` → join; reserved words → double quotes). A failed FedSQL step can report job state `completed`, so the log is always the authority on success.
  - Two tier limits are documented rather than papered over: **a caslib table and a libref table cannot be joined in one statement** on any route (`SESSREF=` makes PROC FEDSQL ignore the LIBS option), and SASHELP is invisible to FedSQL. For `target='cas'` the CAS session is created *and terminated inside the same job* under a per-query name, so nothing outlives the query and a failed query cannot poison the compute session for the next one.

- **`upload_file` can now stage binary files into Content folders** (#37) — the file content can be provided through exactly one of `content` (inline text, the original behaviour), `file_path` (the server reads the bytes off its own disk — binary-safe, gated by `ALLOW_LOCAL_FILE_UPLOAD`, mirroring `upload_data`), or `url` (server-side fetch). A new `parent_folder_uri` argument files the upload into a Content folder (`/folders/folders/{id}`) — the location `%include`/`filesrvc` ingestion needs — instead of landing unfiled. `content_type` now defaults per source: `text/plain` for inline content, else guessed from the file name (`application/octet-stream` fallback). Field feedback: staging a multi-sheet Excel workbook for filesrvc ingestion previously required going around the server to the raw Files REST API.
- **`execute_sas_code` `fresh_session` flag** (#37) — `fresh_session=true` discards the cached compute session before running, so the code starts with no inherited SAS state (equivalent to calling `reset_compute_session` first). The docstring now flags the state-persistence gotcha prominently — a warm session surviving between calls can make re-run checks double-count — and recommends `libname casuser cas;` over log-flooding `caslib _all_ assign;` preambles.

### Fixed

### Changed
- **Stdio auth model overhauled.** Replaced password-grant authentication with a chain of OAuth 2.0 paths, tried in order: (1) token cached by `sas-viya auth loginCode` at `~/.sas/credentials.json` (or `$SAS_CLI_CONFIG/.sas/credentials.json`); (2) token cached by `sas-mcp-login` at `~/.sas-mcp-server/credentials.json`; (3) native device-code flow. The first hit wins. Password grant was deprecated by OAuth 2.1 and failed with `invalid_client` for OAuth clients registered as confidential.
- `src/sas_mcp_server/config.py` — `viya_auth` is now a `PermissiveOAuthProxy` (subclass of `fastmcp.server.auth.OAuthProxy`) so that, when `ALLOW_RAW_BEARER=true`, raw upstream JWTs fall through to the configured `token_verifier` after the standard MCP JWT swap fails. Behaviour is unchanged when the flag is `false`.
- `src/sas_mcp_server/stdio_server.py` — Rewritten around the new auth chain; removed `VIYA_USERNAME`/`VIYA_PASSWORD` reads.
- `examples/configuration.md` — New "Authentication modes — at a glance" overview comparing all five paths; reworked "Authenticating for stdio mode" to cover both `sas-viya` CLI and `sas-mcp-login` paths; updated Gemini CLI section to drop password-grant references; added `ALLOW_RAW_BEARER` and `SAS_CLI_CONFIG` to the environment variables table.
- `README.md` — Added a "Pull pre-built image" snippet with the published tag table; updated the deployment-mode comparison and "Option B: Stdio mode" instructions; new "Programmatic clients with a pre-existing Viya token" section documenting `ALLOW_RAW_BEARER`.
- `examples/docker/setup.md` — Added a "Pulling the pre-built image" section with the tag-to-image-version mapping and a note about signed build provenance.
- `src/sas_mcp_server/config.py` — Added SSL verification bypass via httpx monkey-patch when `SSL_VERIFY=false`
- `src/sas_mcp_server/viya_utils.py` — Respects `SSL_VERIFY` setting for Viya API calls
- `examples/configuration.md` — Added Python registration script instructions and `SSL_VERIFY` to environment variables table
- **Bumped `fastmcp` from `>=2.13.0.2` to `>=3.0.0,<4.0.0`** (major version). v3 made several APIs async and renamed some module paths. The migration in this repo touches:
  - `OAuthProxy(upstream_client_secret=None, ...)` — `""` is no longer accepted.
  - `Context.set_state` / `Context.get_state` are now `async def` (carried from PR #9).
  - `from fastmcp.utilities.logging import get_logger` — top-level `fastmcp.utilities` is no longer re-exported.
  - `from fastmcp.prompts import Message` — module path flattened.
  - `from fastmcp.tools import ToolResult` — module path flattened.
- **`OAuthProxy(valid_scopes=["openid"])`** — required so containerized deployments accept tokens issued only with `openid` (carried from PR #9; fixes OAuth2 under Podman/Docker).
- **SSL monkey-patch in `config.py` is now idempotent** — guarded by `_sas_mcp_ssl_patched` so reloading the module doesn't stack wrappers around `httpx.AsyncClient.__init__`.

### Removed
- **Password-grant stdio authentication.** `VIYA_USERNAME`/`VIYA_PASSWORD` are no longer read by the stdio server. They remain in `.env.sample` (with clearer wording) only because the integration test suite uses the legacy `sas.cli` password grant to acquire test tokens.

### Fixed

- `_make_client` — Removed default `Content-Type: application/json` header that conflicted with multipart form-data uploads

### Tests
- Updated `test_prompts.py` to use the public `mcp.get_prompt()` / `mcp.list_prompts()` API; v3 removed the private `_prompt_manager` attribute the prior tests reached into.
- Updated `test_mcp_server.py` to `await` mocked `Context.get_state`, since v3 makes the method async.
- Switched `test_config.py` from `del sys.modules + import` to `importlib.reload()`. The old pattern created orphan config modules that polluted `httpx.AsyncClient.__init__` and broke later integration tests with empty-message `ConnectError`s.
- `conftest.py` now calls `load_dotenv()` at module top so `SSL_VERIFY` (and friends) are read from `.env` before any `sas_mcp_server` module is first imported; the `viya_token` fixture also gets an explicit `timeout=60.0` on the password-grant request.

- `test_cas_discovery_workflow` now targets `Public.HMEQ` directly (skips if not loaded) instead of picking `caslibs[0]`/`tables[0]`, which was brittle on Viyas with many tables or unloaded source tables.
